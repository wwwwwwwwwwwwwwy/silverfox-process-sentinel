# 银狐进程监视器 · SilverFox Process Sentinel

> 一个面向 Windows 的**桌面级进程行为监视工具**，用于发现银狐（SilverFox）木马及其变种的落地痕迹。
>
> **定位**：不是杀毒软件，也不是 EDR 替代品。它是一套**透明、可读、可改**的检测规则 +
> 一个零依赖的本地监视界面，适合在中招后做人工排查，或者作为理解银狐攻击链的学习样本。
> 能力边界请务必读第五节 —— 它**看不到纯内存执行、rootkit、短命进程**，
> 这些需要内核级方案。

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Python 3.11+](https://img.shields.io/badge/python-3.11%2B-blue.svg)](https://www.python.org/downloads/)
[![Platform](https://img.shields.io/badge/platform-Windows%2010%2F11-lightgrey.svg)]()


基于 CNCERT / 火绒 / FreeBuf / 先知社区等公开技术报告中的真实样本特征构建检测规则库，
共 **61 条规则**，覆盖进程伪装、PPID 欺骗、签名伪造、白加黑侧加载、计划任务持久化、
BYOVD 驱动、hosts 劫持、Defender 排除项篡改等银狐全攻击链环节。

**另含一个独立的「网络心跳规律性」引擎**：银狐在主机上做的一切 —— 伪装、持久化、
白加黑、BYOVD —— 都只是手段，**最终目的就是建立并维持一条通往 C2 的通道**。
C2 要活着就必须周期性回连，而"周期性"在时间序列上留下的是极低的抖动。
本工具直接读 Windows 的**每连接 TCP 字节计数器**（`GetPerTcpConnectionEStats`，
不抓包、不解密、不联网），从时间序列上判断"哪条外联在像机器一样打拍子"。
打开程序即自动开始观测，**观测时长由界面滑块决定**（30 秒 ~ 15 分钟）。

## 一、快速开始

> ⚠️ **如果你的机器开启了「智能应用控制」(Smart App Control)，请用 `.bat` 启动，
> 不要直接双击打包的 `.exe`。**
> 该策略会拦截未签名的自编译程序（`WinError 4551`，事件日志
> `Microsoft-Windows-CodeIntegrity/Operational` Id 3033/3077 可查）。
> 这是 Windows 自身的安全策略在正常工作，**不是程序有问题**，也**不建议为它关闭该策略**
> （关闭后需重置系统才能重新开启）。
> `启动银狐监视器.bat` 走的是已签名的 Python 解释器，不受影响。
>
> 本项目**不附带打包好的 exe**（体积大且必然未签名）。需要单文件分发的话，
> 可以自己用 PyInstaller 打包，参考 `docs` 里的说明或直接：
> `pyinstaller --onefile --noconsole --add-data "app;app" --name SilverFoxSentinel app/main.py`

## 三、检测能力

### 3.1 规则分类

| 前缀 | 类别 | 条数 | 代表规则 |
|---|---|---|---|
| `P` | 进程行为 | 26 | 伪装系统进程、PPID 欺骗、签名伪造、C2 外联、命令行破坏 |
| `N` | 网络心跳 | 5 | 周期性心跳、命中 C2 地址、规律性外联 × 进程高风险联合判定 |
| `T` | 计划任务 | 8 | 冒用系统更新任务名、隐藏高频任务、AI 生成式长句任务名 |
| `S` | 系统服务 | 4 | 服务二进制位于非常规目录、伪装扩展名 |
| `D` | 内核驱动 | 4 | BYOVD 易受攻击驱动、驱动文件伪装扩展名 |
| `H` | hosts 劫持 | 2 | 安全厂商域名被指向回环地址 |
| `R` | 注册表 | 6 | Defender 大面积排除、银狐专用注册表键 |
| `F` | 文件系统 | 3 | 伪装扩展名的 PE 文件、银狐组合落地目录 |
| `X` | 深度扫描 | 3 | 白加黑侧加载、加载伪装扩展名模块 |

### 3.2 评分模型

```
风险分 = min(100, 最高权重 + 0.35 × 其余权重之和)

≥80 严重(critical) | ≥55 高危(high) | ≥30 可疑(medium) | ≥10 关注(low)
```

该模型的设计意图：**避免"5 条低危规则叠加"压过"1 条严重规则"**，
同时保留多条弱信号相互印证时的加成意义。

### 3.3 关键设计取舍

本工具的核心难点不是"能不能检出"，而是**误报控制**。开发过程中做过几轮实测收紧，
以下是几个有代表性的决策（都写在代码注释里）：

- **不凭缺失数据定罪。** 签名"尚未校验"或"校验失败"都不算未签名，
  只有明确判定为 `unsigned / forged / untrusted` 才触发签名相关规则。
  否则首轮扫描会满屏红点。
- **目录判定必须带上下文。** Windows Defender 自身就安装在
  `C:\ProgramData\Microsoft\Windows Defender\Platform\<版本>\` 下，
  按"ProgramData 下的程序可疑"一刀切会把 Defender 判成木马。
  现在 ProgramData / AppData 只在**文件名为随机名或一级子目录为随机名**时才判可疑。
- **随机命名识别要排除品牌名。** `i4Tools`（爱思助手）、`AIDA64` 含数字且大小写混杂，
  朴素启发式会把它们判成随机名。现在先做"是否像英文单词"的音节结构判断。
- **术语匹配必须按词。** 银狐恶意任务名 `Our Empowering Procedure Standardization And`
  里的 "Empowering" 含子串 "power"，按子串匹配会被合法术语表误挡。
- **大目录排除要精确相等。** `C:\Users\<用户名>\AppData\Local\JetBrains\PyCharm2026.1`
  这种正常的开发工具排除项，不能算成"整个 `C:\Users` 被排除"。

### 3.4 实测误报水平

在开发机上（Windows，296 个进程、269 个计划任务、313 个服务、442 个驱动）实测：

| 指标 | 结果 |
|---|---|
| 严重(critical) 误报 | **0** |
| 高危(high) 误报 | **0** |
| 中危(medium) 误报 | 1（正在运行的 `powershell.exe` 带 `-ExecutionPolicy Bypass` 参数） |

该中危项属规则 `P011` 的已知行为：`-ExecutionPolicy Bypass` 在正规安装程序中也常见，
因此本条只给中等权重（50 分），单独出现不会升级为高危。

### 3.5 性能

实测（311 个进程的机器上）：

| 指标 | 初版 | 现在 | 提升 |
|---|---|---|---|
| 稳态单轮采集 | 9081 ms | **62 ms** | **145×** |
| 冷启动首轮 | 9081 ms | 2463 ms | 3.7× |

初版一次性向 psutil 索取全部字段，其中三项是「隐形杀手」：

| 字段 | 311 个进程耗时 | 处置 |
|---|---|---|
| `cmdline` | 5132 ms | 按 (pid, 创建时间) 缓存，每个进程一生只取一次 |
| `num_threads` | 1341 ms | 移到详情视图按需获取 |
| `status` | 1224 ms | 删除（原本没有任何地方用到） |

而 `cmdline` 的 5.1 秒里，**100% 来自 5 个受保护进程**（`LsaIso.exe`、`NgcIso.exe`、
3 个 `WUDFCompanionHost.exe`）—— 每个都要整整 1025 ms 才抛 `AccessDenied`。
它们的 `exe` / `username` / `memory_info` 都是毫秒级，**只有 cmdline 会阻塞**。

处置方式：按映像名记住这类进程（预置 3 个实测确认的名字 + 运行时自动学习），
同时跳过没有真实映像路径的系统伪进程（`System` / `Registry` / `Memory Compression`）。
为避免留下检测盲区，跳过条件额外要求「该进程确实住在 `System32`」——
若木马把映像名伪装成 `LsaIso.exe` 放到用户目录，命令行照常会被读取和分析。

剩余的 2.4 秒冷启动是**操作系统首次枚举进程句柄的一次性开销**（第二次遍历即降到 52 ms），
不是代码问题，只影响启动后的第一次扫描。

### 3.6 接口安全

界面由本地 HTTP 服务提供（仅监听 `127.0.0.1`）。**开发过程中的一次安全审计发现：
初版对 POST 请求不做任何来源校验**，于是任意网页都能用

```js
fetch('http://127.0.0.1:8787/api/kill', {method:'POST', mode:'no-cors',
      body: JSON.stringify({pid: 1234})})
```

这种「简单请求」（`Content-Type: text/plain`，不触发浏览器预检）把请求送到服务端，
而服务端照单全收。实测可成功终止任意进程 —— 也就能调用 `/api/shutdown`
**把监视器本身关掉**。对一个反木马工具来说这是致命的。

现在采用四层校验（全部在服务端强制）：

1. **会话令牌**：每次启动生成随机令牌，注入页面 `<meta>`，POST 必须带 `X-Yinhu-Token` 头。
   自定义头会强制浏览器发预检请求，跨域预检必然失败 —— 请求根本发不出去。
2. **Origin 校验**：浏览器跨域请求必带 `Origin`，非同源一律拒绝。
3. **Host 校验**：必须是回环地址，防 DNS 重绑定。
4. **Content-Type 校验**：必须是 `application/json`，挡掉表单与 `text/plain` 提交。

另外：请求体上限 256 KB（防本地内存耗尽）；`PID 0 / 4` 等系统关键进程在接口层显式拒绝；
`/static/` 路径穿越已拦截。以上均有自动化回归用例覆盖。


### 3.7 已知项机制（让误报可被安全忽略）

安全工具最大的敌人不是漏报，而是**误报导致的告警脱敏** ——
用户被误报烦到之后，真正的告警也不看了。

直接删规则或按规则号全局忽略是**危险**的：那些规则恰恰也是攻击者的常用手法。
本项目改为「**带守卫哈希的已知项**」：

一条已知项 = 「规则号」+「匹配条件」+「**被执行的脚本文件的 SHA-256**」，三者都满足才忽略。

* 匹配条件限定到**具体对象**（如"命令行里必须含 `my-watchdog.ps1`"），不是"凡是这条规则都不报"；
* 守卫哈希绑定**被执行的脚本** —— 内容一旦变化（哪怕一个字节），哈希对不上，
  **忽略立即失效、告警自动回来**。攻击者替换脚本不会被静默放过；
* 守卫文件不存在时同样按"忽略失效"处理（宁可多报，不可漏报）。

用法：在告警详情里点「标记为已知项」，确认框会显示将要绑定的文件与哈希；
「规则与 IOC」页的「安全状态」面板里有已知项列表，可逐条移除。

已知项文件位于 `app/whitelist.json`，**有意放进 `app/` 让它被完整性自检覆盖** ——
绕过界面直接改白名单来掩盖告警，会触发"程序文件已被改动"的严重告警。

### 3.8 第二轮审计：三处自身误报

首轮把误报压到 0 之后，做了一次针对「工具会不会误判自己/系统」的专项审计，
又发现三处 —— 都是**工具在真实环境里会天天遇到**的，不是边角案例：

| 问题 | 现象 | 修正 |
|---|---|---|
| **X003 白加黑规则误判 MSIX 应用** | `pwsh.exe`（PowerShell 7，装在 `D:\WindowsApps\Microsoft.PowerShell_*`）加载同目录的 .NET DLL，被判定为白加黑 | MSIX / Store 应用的 DLL 由**包签名整体保护、不单独做 Authenticode 签名**，因此排除 `\WindowsApps\` 目录 |
| **单条规则重复计分导致分数爆表** | X003 每加载一个可疑 DLL 就产出一条 finding，`pwsh.exe` 一次 15 个 → 15 × 82 分，分数顶到 100 判成「严重」 | 深度扫描改为**按规则聚合**：一条 finding 带模块列表与计数，不再逐条累加 |
| **工具把自己的子进程判成木马** | 签名校验用 `powershell -EncodedCommand` 调用，正好命中 P010「内存加载/下载执行」→ 把自己的校验进程判成严重风险 | ① 排除本工具自己拉起的子进程（`ppid == 自身 PID`）；② 把 `-EncodedCommand` 从 P010 拆成独立的 **P010B**，权重降到中等（55）—— 该手法在 SCCM / Intune / 各类安装程序中同样常见，单独出现不足以定性 |

修正后的真机结果：**严重 0 / 高危 0 / 中危 1**，唯一那条是真实观察 ——
一个上一轮会话遗留的定时任务正在执行
`powershell.exe -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File ...my-watchdog.ps1`
（隐藏窗口 + 绕过策略 + 执行用户目录下的脚本文件，给中等权重是合理的）。

### 3.9 网络心跳检测（银狐的最终目的是连上 C2）

**出发点**：木马在主机上做的一切 —— 伪装、持久化、白加黑、BYOVD —— 都只是手段，
**最终目的就是建立并维持一条通往 C2 的通道**。所以"哪条外联不正常"是最接近本质的检测角度。

**为什么盯"规律性"**：C2 要活着，就必须**周期性**回连（心跳 / beacon）。这是它的生存必需。
而"周期性"在时间序列上留下的是**极低的抖动**：

| 流量类型 | 实测间隔 | 变异系数 CV |
|---|---|---|
| 银狐心跳（无抖动） | 60.0 / 60.4 / 59.8 / 60.1 秒 | ≈ 0.004 |
| 浏览器 / CDN | 0.3 / 12 / 1.1 / 47 / 0.8 秒 | ≈ 1.4 |
| 软件更新检查 | 300 / 300 / 300 秒 | ≈ 0.01（**同样很规律**） |

最后一行是关键：**规律性本身不足以定罪**。所以本引擎输出**两个独立维度**，绝不混为一谈：

- **规律性（0–100）** —— 纯时序指标，由事件间隔的变异系数换算。回答"这条外联有多像机器在打拍子"。
- **风险分（0–100）** —— 由规则判定。回答"这件事有多可疑"。

界面把两者**分列显示、各自高亮**。规律性高但进程可信、目标正常的流量
（例如 Windows 遥测）会出现在"规律"维度里，但不会进入风险告警 ——
这是刻意的：把系统自身的遥测刷成高危，用户三天内就会对告警脱敏，工具也就废了。

**两条互相补充的证据流**

1. **连接建立间隔** —— 覆盖"连上 → 发数据 → 断开 → 再连"型心跳。
2. **数据突发间隔** —— 覆盖**长连接上的心跳**。这条更关键：银狐常见的持久 C2
   是一条一直挂着的 TCP 连接，在连接表上永远是"存在"，
   只有**字节计数**才看得出"每 60 秒推一小段数据"。

**字节计数从哪来**：Windows 自带的 `GetPerTcpConnectionEStats`（与 Wireshark 的
TCP Stream Graphs、`netsh trace` 同源）。它读取的是 TCP 协议栈**已经维护的计数器** ——
**不需要内核驱动、不需要抓包、不改变任何流量**。实测：

```
启用前读取 → 成功但全为 0（未开启采集）
启用后读取 → 立刻拿到累计值（out=14996 / in=9925）
连续采样   → 计数单调不减，且呈「离散突发」形态
              （某连接 25 秒内只在 t=6 出了 1414 字节、t=7 进了 333 字节，其余时刻完全不动）
```

**N 系列规则（5 条）**

| 规则 | 标题 | 触发条件 |
|---|---|---|
| `N001` | 外联呈现周期性心跳 | 规律性 ≥55 **且**（进程签名明确不可信 **或** 端点可疑）。内网目标权重封顶到中危 |
| `N002` | 连接已知银狐 C2 地址（网络会话层） | 会话期间实测到与公开披露 C2 的活动连接 |
| `N003` | 规律性外联 + 进程本身已判高风险 | 规律性 ≥70 **且** 进程风险为 critical/high（两条独立证据共振） |
| `N004` | 未签名程序连接银狐常用非标端口 | 未签名 + 端口命中 18300 / 7000 / 8001 等 |
| `N005` | 高风险进程持有对外连接 | 进程已判 critical/high 且确实握着公网连接（**不依赖规律性**） |

**误报治理（这一块的工作量比检出本身更大）**

| 陷阱 | 处置 |
|---|---|
| **TIME_WAIT 让"重连"看不见** | 客户端关闭后四元组会在 TIME_WAIT 停留 30–120 秒。若把它算作"连接存在"，则"关闭→重连"永远观测不到，重连型心跳会被误判成一条长连接 → **只认 ESTABLISHED / SYN_* / \*_WAIT 等活状态** |
| **持续传输伪装成"极规律"** | 视频流在 1 秒采样下"每次都有增量"，间隔恒为 1 秒 → CV≈0，看起来完美规律。→ 加**静默比例门槛**：只有"长时间静默 + 离散突发"才采用字节证据 |
| **一次心跳被算成两次事件** | 先发后收会在相邻两个采样点各产生一次增量 → 凭空多出一个 1 秒间隔。→ **相邻事件合并**（窗口 = 1.6 × 采样周期） |
| **字节计数回退** | 四元组被新连接复用时计数会跳回小值（实测确认）。→ 识别为"连接实例更换"并重设基准，**绝不把负增量当流量** |
| **系统伪进程被误报** | `noimage`（PID 0/4/308 这类没有可执行文件的）与"签名尚未校验"的进程不能被当成不可信 → 与 `P005` 统一口径，**只认明确的 unsigned / forged / untrusted** |
| **内网规律流量被高估** | C2 服务器在公网。→ 内网目标对 `N001` 权重封顶（`N003` 不受影响，横向移动不能放过） |

**观测边界（必须说清）**

- **采样精度**：默认 1 秒一次。间隔短于采样周期的行为会混叠；
  中位间隔 < 4×采样周期的结论会被标记 `resolution_limited` 并降权。
- **不抓包、不解密**：只看连接表与 TCP 栈计数器，看不到载荷内容。
  "规律性高"是**行为特征**，不能证明那是 C2。
- **UDP 无远端**：UDP 表只有本地端口，无法关联远端，因此只做端口清点，不参与规律性判定。
- **非管理员降级**：读不到字节计数时自动退化为"仅连接建立事件"模式，界面会明确标注
  "长连接型心跳可能漏检"，建议以管理员身份运行。
- **零外联**：不做 DNS 解析、不打开 socket、不发起任何网络请求
  （回归自检里有源码级断言，确保 `netmon.py` / `netapi.py` 不出现任何网络客户端调用）。

**性能**：实测单轮采样 **1–2 ms**（约 30 条活动连接），CPU 占用可忽略。

**会话模型**：一次「检测会话」= 一段固定长度的观测窗口。**打开程序即自动开始**；
滑块随时可调（拖长会延长当前会话，拖短到已过时长之下则立即结算）；
会话结束后结果**冻结**（用户看到的应是那一段观测窗口的结论，而不是随机器状态漂移的数字）。

### 3.10 第四轮：告警时间线里出现了"自己人"

**现象**：告警时间线里出现一条 `high 72.5` —— `pwsh.exe` 命中 `P010B`（Base64 执行）
+ `P011`（绕过执行策略）。把证据里的 Base64 解出来，内容与本工具
`winapi._PS_PREAMBLE` **逐字一致** —— 被报"高危"的是**本工具自己的签名校验子进程**。

**为什么原来的排除失效**：初版只判断"直接父进程是不是自己"（`ppid == self_pid`）。
实测有三种情况会让这个判据失效：

| # | 情况 | 后果 |
|---|---|---|
| 1 | **venv 的 `pythonw.exe` 是启动器**，会再派生一个真解释器；`os.getpid()` 是后者，中间多了一层 | `ppid` 指向启动器 |
| 2 | 经 `%LOCALAPPDATA%\Microsoft\WindowsApps\pwsh.exe`（**MSIX 应用执行别名**）启动时，激活过程可能插入中转进程 | `ppid` 指向 broker/stub，`Popen` 拿到的 PID 也可能是 stub |
| 3 | **监视器被强制结束时，子进程变成孤儿**（父进程已死） | 父进程关系彻底失效，且会**残留**到下次启动才被发现 |

第 3 种最隐蔽：孤儿一直挂在进程表里，下次启动的实例看到它，既不是自己的子进程、
也不在自己的登记表里 → 判成高危。

**修复（四层，缺一不可）**

1. **按 PID 精确登记**：`run_ps` 用 `Popen` 拿 PID，连同创建时间登记进
   `winapi._OWN_CHILDREN`；规则引擎按 `(pid, create_time)` 排除（创建时间用于防 PID 回收误伤）。
2. **祖先链判据**：最多回溯 6 层，链上出现本进程即排除 —— 覆盖第 1 种情况。
3. **启动真实解释器、绕开应用执行别名**：从注册表的 MSIX 包仓库解析出 `pwsh.exe`
   真实安装路径并直接启动 —— 覆盖第 2 种情况，顺带省掉一次 MSIX 激活开销。
4. **Job Object 兜底**：把每个辅助子进程放进带 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job，
   监视器一旦消失（包括被任务管理器强杀），子进程由内核连带回收 ——
   **从根上消灭孤儿**，覆盖第 3 种情况。

> ⛔ **判据绝不能放宽成"命令行里含本工具 preamble 就放过"** ——
> 那是一条**免杀通道**：攻击者读一遍源码就能把自己的 PowerShell 前缀成同样的
> preamble，从此对本工具隐身。父进程链可以伪造，PID + 创建时间不能。
> `tools/回归自检.py` 里有一条专门的守卫断言防止日后有人那样"简化"。

**⚠️ 仍然存在的边界**：同机同时运行**两份本工具的副本**时，两个实例会互相把对方的
签名校验进程报成高危（彼此不是对方的子进程）。单实例运行不会出现；
遇到时用「已知项」忽略即可。**不建议**为此引入跨实例的宽松判据。

### 3.11 第五轮：报告顶部说"0 高危"，下面却列一堆"高危"

**现象**（试用者反馈）：导出的排查报告里，顶部方框写着"高危 0"，
下面的表格却列出一堆标着"高危"的行。

**根因**：顶部 KPI 的计数直接取自 `summary.levels`，那**只统计进程**；
而下面的表格除了异常进程，还列了**系统痕迹**（计划任务 / 服务 / 驱动 / …）。
两处口径不同 —— 一台"没有高危进程、但有若干高危系统痕迹"的机器上，报告就会自相矛盾。

**顺带发现的同类问题**：结论摘要在只有"中危"项时也会说"未发现银狐相关高风险特征"，
而表格里明明列着中危行。

**修法（结构上杜绝，而不是改数字）**

1. 把报告的**行**与**计数**收进同一个函数 `report_buckets(st)` ——
   计数与表格行同源，改一处即同时改两处，**结构上不可能再对不上**。
2. 顶部 KPI 改为**跨类别合计**（严重项 / 高危项 / 异常项合计），
   并在结论摘要下方加一张**按类别分列的分级表**（异常进程 / 系统痕迹 / 网络外联 / 合计），
   与下方三张表**逐行对应**。
3. 各章节标题带上项数（"二、异常进程 —— 3 项"），读者可当场核对。
4. 结论摘要按合计分级判断，**覆盖只有中危/低危的情况**。
5. 第五节详情卡从"仅进程"扩展为"进程 + 系统痕迹"，与"需处置 N 项"一致。
6. 明确区分**风险项**与**规律性观察项**：后者标"观察"、不计入任何风险等级，
   并在标题里单独计数。

**验证**：新增 16 项断言，核心一条是 **"顶部计数 == 表格里对应等级的行数"**。
报告生成已拆成纯函数 `build_report_html(st)`，正是为了能用合成数据做这类结构测试。

**术语调整**：界面上的「系统制品」改叫**「系统痕迹」**（"制品"是 artifact 的直译，
属于行话），并在页签顶部加了一句说明。


### 3.12 界面文案：专业用语版 / 大白话版（可切换）

**起因**：用户看完界面后要求"把那些东西都翻译成大白话，再设一个开关切换专业版和大白话版"。
更根本的理由是：这套工具的规则是按公开技术报告写的，术语密度很高（制品、外联、规律性、
变异系数、IOC、PPID 欺骗…）。**懂行的人看术语更快更准，不懂的人看术语只会一脸问号 ——
一个安全工具如果让人看不懂，就等于没有。**

**做法**：右上角一个两档开关，选择记在 `localStorage`，**默认大白话**。

| | 专业用语版 | 大白话版 |
|---|---|---|
| 页签 | 进程监控 / 网络监控 / 系统痕迹 | 运行中的程序 / 联网行为 / 系统里留下的东西 |
| 表头 | 风险 / 路径 / 数字签名 / 命中规则 | 危险程度 / 文件位置 / 官方签名 / 为什么被标记 |
| 等级 | 严重 / 高危 / 中危 / 低危 | 严重 / 可疑 / 留意 / 轻微 |
| 网络 | 规律性 / 远端地址 / 观测时长 | 规律程度 / 连到哪里 / 检查多久 |
| 规则名 | 伪装系统进程 / 命令行静默绕过策略 | 冒用系统程序的名字 / 绕过了脚本执行限制 |

**三条设计约定**（写在 `app.js` 的注释里，改的时候不要破）：

1. **大白话版只换说法，不换含义，也不弱化等级** —— `critical` 仍然是"严重"。
   安全工具里把"严重"说成"可能有点问题"，会让人漏掉真正该立刻处理的事。
2. **涉及可核验事实的地方两版一致** —— 规则号、证据原文、文件路径、哈希都不翻译。
   那些是要拿去核对的，翻译反而添乱。
3. **规则名按规则号映射**（`RULE_PLAIN`），查不到就回退原名 ——
   日后新增规则不会显示成空白。

**顺带**：规则与 IOC 页在大白话模式下会多一句
"这一页是技术细节，看不懂可以直接跳过" —— 与其把密集的技术说明翻得半生不熟，
不如明确告诉用户这一页可以跳过。该页的 IOC 清单、规则描述仍保留原文（那是核对依据）。

**验证**：新增 19 项界面断言（默认大白话 / 切到专业版 / 刷新后记住选择 /
两种语言下的页签、表头、说明条 / 控制台无错误），并逐屏截图人工核对。

### 3.13 第六轮：驼峰品牌名被当成「随机命名目录」

**起因**：一名测试人员（`LAPTOP-B23G59QJ`）导出的报告显示 7 条「系统痕迹异常」，
其中 6 条被标为**严重**（100 / 90 / 85 分），结论写着
"发现严重风险项，高度疑似银狐木马活动"，而**异常进程一栏是 0 条**。
使用者直接问：这些到底是真的还是误报？

**排查结论：6 条里 4 条是纯误报，1 条是误报源（扫描范围过宽），1 条需人工核实。**

| 报告中的项 | 判定 | 根因 |
|---|---|---|
| 计划任务 `DocUpdate`（`Program Files (x86)\MasterPDF\`） | **误报** | `looks_random("MasterPDF") == True` |
| 系统服务 `DocService`（同上） | **误报** | 同上 |
| 系统服务 `MySQL80`（`Program Files\MySQL\`） | **误报** | `looks_random("MySQL") == True` |
| 系统服务 `WXWorkUpgrader`（`Program Files (x86)\WXWork\`） | **误报** | `looks_random("WXWork") == True` |
| 文件特征「伪装扩展名的 PE 文件 共 5 个」 | **误报** | 整目录遍历 `Program Files (x86)`，撞上正常软件的资源文件 |
| 计划任务 `ScreenShareClientUpdate`（`AppData\Local\Temp\`） | **需人工核实** | 命中强信号目录，属设计内告警 |

**根因**：`looks_random()` 的判据是"含大写又含小写 → 随机"。
驼峰式品牌名（`MySQL` / `WXWork` / `MasterPDF`）**全部满足**这一条。
`S004` 因为叠加了"签名不可信"条件所以没误报；
而 **`T004` / `T006` / `S002` 是目录级判断，手上只有路径字符串、拿不到签名，
于是直接定罪** —— 这也说明第 5.x 节原先那句"调用处一律叠加未签名条件"与实现不符，
本次一并修正。

**修法**（新增 `looks_random_dir()`，只用于目录名场景，不动进程名 / DLL 名的判据）：

- 含数字的随机名（`SXRh6d` / `VBV4HZ` / `cgL18U72` / `O02PwqGh` / `Pl6VgrWG`）→ 沿用原判据；
- 不含数字的 → 统计**大小写切换次数**，≥3 次才算随机。

依据：驼峰品牌名只在"词首"切换大小写（`My|SQL`、`Master|PDF`、`WX|Work`），切换 ≤2 次；
随机名的大小写是散乱交替的（`bcCfOw` 切换 4 次，`XsOewfN` 切换 4 次）。

> 两个踩过的坑，已写进代码注释防止被"优化"回去：
> ① 不能用"含元音"当判据 —— `MySQL` 里根本没有 a/e/i/o/u（y 不算）；
> ② 不能用 `re.findall(r"[A-Z][a-z]*|[a-z]+")` 切分再看"是否出现单字母片段" ——
> `[a-z]*` 是贪婪的，`bcCfOw` 会被切成 `['bc','Cf','Ow']`，单字母特征被吃掉，判据失效。

**同时收紧的两处**：

1. `_SUSPECT_SCAN_DIRS` 不再整目录遍历 `Program Files (x86)`，改为只下钻
   **随机命名的一级子目录**（银狐的落点特征）；并给 `F001`（伪装 PE）加了一道
   "强信号上下文"闸：文件须位于 `Public` / `Temp` / `Downloads` / `Recycle.Bin` 之下，
   或路径中存在随机命名目录。正常软件目录里的 `.dat/.db/.ico` 资源文件不再定罪。
2. `T004` 与 `T006` 去重 —— 同一任务原先被两条规则各计一次分
   （`85 + 0.35 × 78 = 112` → 截断成 100），把"中等置信度"顶成了"严重 100 分"。
   现在高权限任务只报 `T006`。

**验证**：新增 29 项断言（品牌名不误报 / 银狐随机名仍检出 / 四条误报路径不再命中 /
`Temp` 与 `Public` 仍命中 / 端到端 `DocUpdate` 任务零告警 / 同一任务落在随机目录时仍报 `T006`），
回归自检 136 → **165 项，全部通过**。

**留下的边界**：`XsOewfN` 这类"大小写混杂、无数字、元音比例又恰好正常"的随机名，
仍会被 `_wordlike` 判成"像词"而漏过目录级判据（属 `looks_random` 的既有局限，见第 5.x 节）。
该样本已在 `MALICIOUS_FILENAMES` 中，由 `S001` / `F002` 兜底。


### 3.14 版本号 与 本机副本管理（解决"我跑的到底是哪一版"）

**起因**：用户问"GitHub 上的是最新版吗""把我桌面上那个也弄成最新版的"。
排查中发现真正的麻烦是 —— **这套工具原本没有任何版本号**。后果是实打实的：

- 本机同时存在多份副本（安装版 / 开源副本 / 一个 2026-10-04 打包的 exe /
  Temp 里一份旧测试副本 / 4 个 PyInstaller 解包残留），**谁新谁旧只能靠文件时间猜**；
- 界面长得都一样，用户以为"都是最新的"，实际跑着旧副本，然后以为功能坏了；
- 每次同步都要人工核对 md5，很容易漏。

**做法一：加版本号**（`app/version.py`）

- `VERSION` = `年.月.日.序号`，例如 `2026.10.05.3`；`BUILD` 是构建时刻。
- **界面左上角标题下常显**（`v2026.10.05.3`），安全状态页与导出的报告里也带。
- `version.compare()` 逐段按数字比、段数不同按 0 补齐 ——
  这样 `2026.10.05` 与 `2026.10.05.0` 视为相同，不会因为写法差异误判。
- ⚠️ **改了 `app/` 下任何文件就要递增 VERSION**，否则副本管理器会误判。
  管理器会检测"同一版本号却有多份不同内容"并报警。

**做法二：本机副本管理器**（`本机副本管理.py` + `检查本机副本.bat`）

```
检查本机副本.bat                      # 双击：只检测，列清单，不改任何东西
python 本机副本管理.py --clean         # 清理：解包残留 / 过期的打包 exe / Temp 旧副本
python 本机副本管理.py --update <目录>  # 把比该目录旧的副本完全覆盖成它
```

**四条安全约定**（写在脚本注释里，改的时候不要破）：

1. **默认只检测、不动任何文件**；要改必须显式给 `--clean` / `--update`。
2. **改之前先备份**到 `<目标>/备份/更新-<时间戳>/`，并在屏幕上列出每个受影响路径。
3. **清理一律"移入暂存"而不是永久删除** —— 判断失误还能捞回来。
4. **绝不碰用户数据**：`%LOCALAPPDATA%\SilverFoxSentinel\`（白名单 / 完整性基线 /
   报告）、目标目录里的 `python_path.txt`（记录本机解释器位置）与 `备份/`。

**⛔ 一条关键闸门：脱敏副本与完整副本绝不能互相覆盖。**

开源副本做过脱敏替换（真实计划任务名 → 占位符、真实用户名 → 占位符）。
两种方向都危险：

- 脱敏副本 → 安装版：工具会**认不出本机真实的计划任务名**，等于功能失效；
- 安装版 → 脱敏副本：会把**真实用户名、真实路径推到公开仓库**，属信息泄露。

所以 `do_overwrite` 会先比对两边的脱敏状态，不一致就**直接拒绝**并说明原因。

**验证**：新增 19 项断言（版本号比较的 6 种情形、脱敏判定的正反向、
**两个方向的越界覆盖都必须被拒绝**、覆盖后 `python_path.txt` 必须保留、
覆盖前必须已备份）。回归自检 173 → 192 项。

## 五、能力边界（请务必阅读）

这是一个**行为检测辅助工具**，不是杀毒软件，也不是 EDR。它的确定性局限：

**检测不到的场景**

- **纯内存执行**：银狐常用"读同目录 jpg/xml → 解密 shellcode → 内存执行"，磁盘上无 PE 落地。
  用户态轮询式监控看不到这类行为，需要 EDR 的内核回调 / ETW。
- **内核级隐藏**：若已加载 rootkit 驱动隐藏进程，本工具读到的进程列表本身就是不完整的。
- **BYOVD 之后的静默期**：银狐用易受攻击驱动强杀安全软件后，其行为可能不再产生可观测事件。
- **短命进程**：默认 3 秒采样一次，存活不足一个采样周期的进程会被漏掉。
- **DLL 注入到合法进程**：注入后的恶意代码在合法进程地址空间内运行，进程名与路径都正常。
  本工具只能通过"加载了非常规模块"间接发现，且需要管理员权限。

**权限限制**

| 能力 | 普通用户 | 管理员 |
|---|---|---|
| 进程列表 / 命令行 / 路径 | 大部分可读 | 完整 |
| 全局网络连接归属 | 部分缺失 | 完整 |
| **每连接字节统计（网络心跳）** | ❌ 读不到 | ✅ |
| Defender 排除项读取 | ❌ 读不到 | ✅ |
| 受保护进程的加载模块 | ❌ | ✅ |

**网络心跳检测的专有局限**

- **不抓包、不解密**：只看连接表与 TCP 栈计数器，看不到载荷内容。
  "规律性高"是行为特征，**不能证明那是 C2** —— 软件更新检查、遥测上报同样很规律。
- **短于采样周期的心跳会被漏掉**：默认 1 秒采样，若心跳间隔本身接近 1 秒会发生混叠。
- **无远端信息的长连接无法给出规律性结论**：一条一直挂着、又完全不传数据的连接，
  在时间轴上没有结构可分析 —— 工具会如实显示"不可评估"，而不是编一个数字。
- **UDP 不参与规律性判定**：UDP 表没有远端地址，只能做端口清点。
- **需要管理员权限才能看到字节计数**：普通用户下退化为"仅连接建立事件"模式，
  重连型心跳仍可检出，**长连接型心跳可能漏检**（界面会明确标注）。
- **不阻断**：只观测与告警，不拦截连接。

**其他**

- 无法替代全盘杀毒扫描与专业 EDR。
- 规则基于公开报告，银狐是持续迭代的黑产工具，新变种可能绕过现有规则。
- 采样式监控天然存在时间窗口，不是实时阻断。
- **受保护进程（PPL / 安全隔离）的命令行无法读取**（`LsaIso.exe`、`NgcIso.exe`、
  `WUDFCompanionHost.exe`），工具会标注「受保护进程，系统拒绝读取」而非静默留空。
  这些进程的路径、签名、网络连接、加载模块等其它维度仍然正常参与检测。

### 5.x 「名字随机性」启发式的实测局限（重要）

银狐会用随机命名（`SXRh6d` / `cgL18U72` / `bcCfOw`）来逃避识别，
本项目用启发式判断"名字是否像随机串"。**这个启发式有明确的天花板，如实公布：**

在真实语料上（**1470 个**合法名字：进程名、服务名、驱动名、计划任务名、
`Program Files` 子目录名）实测：

| 指标 | 数值 |
|---|---|
| 把合法名字误判为随机 | **176 / 1470 ≈ 12%** |
| 漏判真实随机名 | 3 / 18 |

误判集中在 Windows 自带的服务/驱动缩写名上，例如
`AppIDSvc`、`BthA2dp`、`ApxSvc`、`CDPSvc`、`AmdPPM`、`AsyncMac`。

**为什么实际使用中没有暴露成误报**：这条启发式**本应只作加分项** ——
`S004` / `P007` / `R005` 等调用处确实叠加了"未签名 / 根证书不受信任"条件才定罪，
而系统服务与驱动都有微软签名，因此不会触发。

> ⚠️ **2026-10-05 修正**：但 `T004` / `T006` / `S002` 这三个**目录级**调用点做不到这一点 ——
> 它们手上只有一个路径字符串，拿不到签名，于是直接定罪。
> 实测因此把 `MySQL` / `WXWork` / `MasterPDF` 这类驼峰品牌名判成"随机命名目录"，
> 在一台测试机上产生 4 条**严重**误报（详见第 3.13 节）。
> 现已为目录名场景改用更严的 `looks_random_dir()`。

**仍然存在的风险**：如果你机器上有**未签名**的软件，且它的名字恰好是这种缩写风格，
可能被报为可疑。用「已知项」忽略即可。

我们做过参数扫描（元音比例阈值、连续辅音阈值、大小写跳变次数等组合），
**没有任何一组参数能同时降低误报与漏报** —— 这是"按名字猜随机性"这一思路的固有限制，
不是实现问题。改用它需要真正的统计模型（字符 n-gram / 困惑度），那会显著增加依赖与开销，
本项目选择了"保持轻量 + 如实说明"。

## 六、发现威胁后的处置流程

> ⚠️ 银狐具备多阶段冗余设计：CNCERT 报告指出其执行链设置 6 个计划任务，
> **清除单个环节后其余载荷仍可运行**。只杀进程几乎必然被重新拉起。

1. **先取证，后清理。** 立即用「导出报告」保存当前状态（含哈希与完整路径）。
   条件允许时先对内存做镜像——磁盘上可能几乎没有痕迹。
2. **断网。** 拔网线 / 关 Wi-Fi，阻断 C2 与横向移动。
3. **不要急着关机。** 关机可能触发部分变种的破坏逻辑，也会丢失内存证据。
4. **按顺序清理**（每一步都做，不能跳）：
   - 计划任务（重点：`\Microsoft\Windows\AppID\` 下的、隐藏的、每分钟重复的）
   - 系统服务与内核驱动（`driverquery` 核对）
   - 注册表 `Run` 键与银狐专用键（`HKLM\SOFTWARE\JDBCC`）
   - Defender 排除项（`Exclusions\Paths` / `Exclusions\Processes`）
   - hosts 文件中的回环劫持条目
   - 常驻目录（`C:\Users\Public\`、`C:\ProgramData\`、`C:\Windows\Temp\`、`%APPDATA%`）
5. **改密码。** 尤其是财务系统、即时通讯（银狐主要目标是财务人员与 IM 账号）。
6. **全盘杀毒；企业环境建议直接重装。** 银狐的免杀与持久化能力使得"清干净"很难验证。
7. **上报。** 企业用户应同步安全团队；可向 CNCERT 报送样本与 IOC。

    ├── e2e_integrity.py        # 完整性自检的双向验证

```
%LOCALAPPDATA%\SilverFoxSentinel\          ← 运行期数据（每用户一份）
├── reports/                     # 导出的排查报告
├── .app-window/                 # 应用窗口的独立浏览器配置（约 90 MB，可随时删除）

├── integrity.baseline.json      # 完整性基线
└── whitelist.json               # 已知项
```

**为什么要分开**：程序目录可以被收紧成「仅管理员可写」（见第 9.7 节），
那样普通用户就改不了 `python_path.txt` 去劫持启动器。
但程序运行期必须写端口/令牌/基线/报告 —— 这些不能落在只读目录里，
否则非管理员运行会直接失败。所以两者分离：**代码只读、数据可写**。
（数据目录不可写时会依次退回 `%TEMP%` 与程序目录，保证任何环境下都能跑。）

**技术选型说明**：界面采用「本地 HTTP 服务 + 浏览器应用模式窗口」而非 Electron / WebView2。
好处是零额外运行时依赖、部署体积几乎为零，界面表现力与原生应用一致。
数字签名校验使用 Windows 原生 `Get-AuthenticodeSignature`（批量调用 + 增量缓存），
可识别**"内嵌签名但摘要校验失败"**这一银狐伪造签名的确凿特征。
网络采集使用 Windows 原生 `GetExtendedTcpTable` / `GetPerTcpConnectionEStats`
（ctypes 直接调用，**无第三方依赖、无内核驱动、无抓包**）。

## 九、安全性说明（威胁模型 · 加固措施 · 能力边界）

### 9.1 它会不会被篡改？——**会，而且必须承认这一点**

**实测证据**：程序目录的 ACL 显示，`NT AUTHORITY\SYSTEM`、`BUILTIN\Administrators`
和当前用户账户对本目录都是 `FullControl`。而本工具以当前用户身份运行。
结论：**任何以相同权限运行的恶意程序，都可以直接修改规则文件、或者干脆结束本进程。**

这不是本工具特有的缺陷，而是所有**用户态**安全工具的固有上限。专业 EDR 靠两样东西解决它：
内核驱动 + 以 **PPL（受保护进程）** 身份运行 —— 后者需要 EV 代码签名证书并通过微软审核，
纯 Python 脚本做不到。

**已实现的缓解：程序文件完整性自检**

- 首次运行为 `app/` 下全部代码与前端文件建立 SHA-256 基线，此后每次启动、
  以及运行期间每 5 分钟重新比对；
- 一旦发现文件被改动，**顶栏状态灯变红**、告警时间线出现严重级告警、
  「安全状态」面板列出被改动的具体文件；
- 也可以在命令行独立校验：`python app\main.py --verify-only`
  （正常退出码 0，检测到改动退出码 2，便于脚本化）；
- 确认改动是自己做的（例如更新了 IOC）后，可在界面上重建基线。

**这个机制能做什么、不能做什么（说清楚）**

| 能做 | 不能做 |
|---|---|
| 发现意外损坏（磁盘错误、拷贝不完整、更新中断） | 发现"攻击者同时改了代码和基线"的情况 |
| 发现**顺手改一把**的普通恶意程序（绝大多数木马不会专门针对本工具做免杀，更可能粗暴替换规则文件） | 阻止攻击者直接结束本进程 |
| 让用户随时确认手上的副本没被人动过 | 阻止攻击者给本程序打补丁 |

**要真正抗篡改，正确做法是**：把程序装到受保护目录（如 `C:\Program Files\`），
由管理员控制文件写权限，并以专用低权限账户运行界面。这属于部署层面的加固，
本工具不自动做（因为会显著提高使用门槛）。

### 9.2 它会不会给其他攻击留下漏洞？——已实测，并修掉了一个真问题

**实测的攻击面**（脚本 `_dev/audit_surface.py` 可复跑）：

| 项目 | 实测结果 |
|---|---|
| 监听范围 | `127.0.0.1:8787`，**只绑回环地址**；从局域网 IP `192.168.1.50:8787` 连接被拒（ConnectionRefused）；未绑定 `0.0.0.0` |
| 网络外联 | 运行 40 秒，该进程及其全部子进程的**非回环连接数 = 0** |
| 子进程 | 仅签名校验期间短暂出现的 PowerShell（校验完即退出） |
| 运行权限 | 当前用户（**不是** SYSTEM） |

**修掉的一个真实注入隐患**：签名校验需要把一批文件路径交给 PowerShell。
初版是把路径**拼进脚本文本**（`$paths=@('...','...')`）——
虽然转义了单引号，但 Windows 文件名在 NTFS 原生接口下可以包含**换行等控制字符**，
而待校验路径来自**进程枚举**（攻击者可控输入），理论上可注入额外语句；
而这些 PowerShell 是以当前用户（通常是管理员）身份运行的。

修正：① 剔除含控制字符的路径；② 路径改为**经临时文件传递**，彻底不做字符串拼接。

**已实现的写操作防护**（详见 3.6 节）：会话令牌 + Origin 同源 + Host 回环 + Content-Type
四层校验，另有请求体上限、受保护 PID 拒绝、静态文件路径穿越校验。
9 条攻击路径的自动化回归用例全部通过。

**仍然存在的风险（诚实列出）**：

- 以管理员身份运行时，本进程被攻破即等于管理员权限失守 —— 因此**不建议长期以管理员身份挂着**，
  只在需要完整检测能力时临时提权；
- 报告导出为 HTML 文件，用浏览器打开时理论上存在本地 HTML 的常规风险
  （内容已做转义，且数据来源是本机进程信息）；
- 界面依赖 Edge 渲染，浏览器的漏洞面属于 Edge 而非本工具。

### 9.3 检测内容真不真？——分级标注来源

**规则里没有一条是我编的。** 但来源的可靠度分两档，应当说清楚：

| 来源档位 | 具体来源 | 说明 |
|---|---|---|
| **一手（逐字摘录）** | CNCERT & 天融信《关于"银狐"木马"甲蚁（G01）团伙攻击态势深入分析报告》2026-09 | 我下载了官方 PDF 并用 pypdf 提取全文，IOC 是**逐字摘的**。计划任务名、落地路径、C2 地址、伪造签名主体、Defender 排除项等均出自此报告 |
| **二手（网页摘要）** | FreeBuf 七阶段攻击链分析、火绒安全实验室 BYOVD 分析（看雪论坛转载）、先知社区应急复盘、博客园 DoH 变种逆向 | 通过网页抓取 + 摘要获得。**具体字符串可能与原文有出入**，建议以原文为准 |

**我做不到的事（必须说明）**：我**没有拿到任何银狐样本**，
因此无法独立验证每条 IOC 的准确性，也无法确认这些 IOC 当前是否仍在被使用。
IOC 会随木马迭代失效 —— 银狐是"黑产 SaaS"式持续运营的家族，
CNCERT 报告明确指出其**服务端按次打包载荷、同名文件哈希各不相同**，
所以基于固定文件名的黑名单本来就容易被绕过。

**这也是为什么规则引擎的重心是行为特征而不是 IOC**：
即使所有 IOC 全部过期，"伪装系统进程 + 签名伪造 + 计划任务持久化 + BYOVD 驱动 + hosts 劫持"
这些行为规则依然有效。IOC 只是加分项。

### 9.4 和专业检测工具差在哪里？

| 能力 | 本工具 | 专业 EDR / 杀毒软件 |
|---|---|---|
| 进程创建事件 | **3 秒轮询**，存活不足一个周期的进程会漏 | 内核回调 `PsSetCreateProcessNotifyRoutineEx`，零漏报 |
| 无文件/纯内存执行 | **看不到**（银狐主力手法） | ETW Threat Intelligence + 内存扫描 + AMSI |
| DLL 注入 | 只能靠"加载了非常规模块"间接推测 | 内核回调 + 内存区域权限检查（RWX 检测） |
| 网络层 | 只读本机连接表与 TCP 栈计数器（无域名、无内容） | 网络流量解析、DNS/HTTP 层检测、NDR |
| 心跳 / beacon 检测 | **有**：基于连接建立间隔与每连接字节突发的规律性（变异系数） | 有，且可结合域名信誉与 JA3/JA4 指纹 |
| 抗篡改 | 用户态自校验，可被同权限攻击者绕过 | 内核驱动 + PPL 保护 |
| 实时阻断 | **不能**，只能事后告警 | 可在行为发生前拦截 |
| 文件特征库 | 无 | 百万级特征 + 云查杀 + 机器学习 |
| 处置能力 | 结束进程、打开文件位置 | 隔离、回滚、全网联动 |
| 免杀对抗 | 无 | 持续更新 + 沙箱 + 动态行为分析 |

**它比专业工具强的地方只有两点**，但这两点对个人用户确实有价值：

1. **完全透明**：61 条规则、全部 IOC、每一条的判断依据都写在明文文件里，你可以逐条读、
   逐条改。商业 EDR 的规则引擎是黑盒。
2. **零依赖、零联网、零成本**：不需要控制台、不需要订阅、不上传任何数据。
   适合做"第一时间的自查"，或者作为专业工具的补充视角。
   —— 网络心跳检测同样遵守这条：只读本机内核计数器，**不做 DNS 解析、不发起任何请求**。

**一句话定位**：它大致相当于"Sysinternals + 一套定制排查脚本"的自动化版本，
**不是 EDR 的替代品**。中招之后想彻底确认是否清除干净，仍然需要专业工具或重装系统。

### 9.5 能不能完全本地化、不联网、不开网页？

**联网方面：本来就不联网。** 实测 40 秒内该进程及全部子进程的**非回环连接数为 0**；
程序内没有任何向外部服务器发送数据的代码路径。所有采集数据只存在于本机内存、
以及你主动导出的报告文件里。

**"不开网页"方面：目前做不到完全脱离浏览器。** 这是一个明确的设计取舍：

- 界面是**本地**页面（`http://127.0.0.1:<端口>`），不经过任何网络；
- 但它需要 Edge/Chrome 作为渲染引擎（以 `--app` 模式开一个无地址栏的独立窗口）；
- 选这个方案的原因：**零额外运行时依赖**。用 Electron 要拖进来上百 MB，
  用 tkinter 则界面表现力明显不足（且部分 Python 发行版不自带 tkinter）。

如果你确实要求"完全不使用浏览器"，有两条路，都需要额外安装东西：

1. 改用 tkinter 重写界面 —— 彻底脱离浏览器，但界面会明显变朴素；
2. 用 `pywebview` 换成 WebView2 内核 —— 本质上仍是网页渲染，只是不显示浏览器外壳。

**当前方案的实际风险**：本地页面不暴露到网络，浏览器只用来渲染本地内容，
不加载任何远程资源（页面带 CSP 头，`script-src 'self'`）。

### 9.6 端口能不能检查、能不能改？

**能查。** 三种方式：

1. **界面**：「规则与 IOC」页顶部的「安全状态」面板直接显示 `监听地址 127.0.0.1:8787`；
2. **文件**：程序运行时会把自己实际使用的端口写入 `runtime_port.txt`；
3. **命令行**：`netstat -ano | findstr LISTENING | findstr 127.0.0.1`，
   再用 `tasklist /FI "PID eq <PID>"` 对上是哪个进程。

**能改。** 支持命令行参数：

```bat
python app\main.py --port 9000          :: 指定端口
python app\main.py --no-window          :: 只起服务，不自动开窗口
python app\main.py --host 0.0.0.0       :: ⚠ 会开放给局域网，不建议
python app\main.py --verify-only        :: 只做完整性校验后退出
```

端口范围默认在 `8787-8816` 之间自动挑选空闲端口。
指定 `--host` 为非回环地址时会打印醒目警告 —— 那会让同网段的其他机器访问到你的进程列表，
**强烈不建议**。

**顺带回答"工具能不能检查端口"**：能。规则 `P025` 会标记"无签名程序 + 用户目录 + 监听端口"
的组合；界面进程详情里每个进程都列出它的网络连接与监听状态。

### 9.7 威胁模型：同用户攻击者能做什么、我们怎么应对

这是用户态安全工具绕不开的问题，如实说清。

**前提**：攻击者已经能以你的身份运行代码（这是反木马工具的常规假设）。

| 攻击手法 | 是否可行 | 应对 |
|---|---|---|
| 直接结束监视器进程 | ✅ 可行 | 无法防御（无内核驱动/PPL）。这是所有用户态工具的固有上限 |
| 改 `app/rules.py` 删掉检测规则 | ✅ 可行（若程序目录可写） | 完整性自检会报「程序文件已被改动」 |
| 改 `python_path.txt` 让启动器执行他的程序 | ✅ 可行（若程序目录可写） | **程序目录已收紧为仅管理员可写**（见下） |
| 删掉基线文件让自检哑火 | ✅ 可行 | 哨兵文件在独立位置，会报「基线丢失」 |
| 加一条已知项掩盖自己的告警 | ✅ 可行 | 已知项**绑定被执行文件的 SHA-256**，文件一变忽略即失效 |
| 用「加入已知项」这个日常操作洗白篡改 | ✅ 曾可行 | 已修：基线刷新**只接受 `whitelist.json` 的差异**（见下） |

**关键加固一：程序目录收紧为仅管理员可写**

`D:\<程序目录>` 默认继承 `Authenticated Users: Modify` ——
任何登录用户都能改 `python_path.txt`，让启动器去执行他的程序，
而**监视器根本不会启动，自检告警永远不会出现**。
所以光靠"把配置文件纳入基线"救不了场，必须做结构性修复：

```powershell
# 以管理员身份执行（把 <路径> 换成实际程序目录）
icacls "<路径>" /inheritance:d /T /C
icacls "<路径>" /remove:g "NT AUTHORITY\Authenticated Users" "BUILTIN\Users" /T /C
icacls "<路径>" /grant:r "NT AUTHORITY\Authenticated Users:(OI)(CI)(RX)" /T /C
icacls "<路径>" /grant:r "BUILTIN\Administrators:(OI)(CI)(F)" /T /C
icacls "<路径>" /setowner "BUILTIN\Administrators" /T /C
```

⚠️ **在 Program Files 下新建文件夹时，创建者账户会被自动授予 FullControl** ——
"放在 Program Files 就安全"这个假设不成立，必须显式清理 ACL。

**关键加固二：完整性基线刷新不再"全量赦免"**

曾经的实现是：界面上增删一条已知项 → 重算 `app/` 下**全部文件**的哈希并整体覆盖基线。
这是个严重漏洞 —— 攻击者改掉 `rules.py` 后，用户只要对**任何一条无关告警**
点一次「加入已知项」，篡改就被写进新基线、告警消失，而触发动作完全日常。

现在的语义：**除 `whitelist.json` 之外的任何差异都拒绝刷新**，
保留完整性告警并把差异清单返回给界面展示。
全量重建只保留给界面上那个显式按钮（用户明确知道自己在做什么）。

**关键加固三：`python_path.txt` 纳入完整性基线**

启动器会执行它里面写的解释器路径，所以它必须被自检覆盖 ——
改动会触发「程序文件已被改动」。启动器还会**回显实际使用的解释器路径**，
被换成陌生路径时一眼可见。

**仍然做不到的**（不要抱幻想）：

- 攻击者可以直接 `taskkill` 结束监视器 —— 用户态工具无法阻止
- 攻击者若能提权到管理员，上述 ACL 保护即失效
- 纯内存执行、rootkit、DLL 注入到合法进程 —— 需要内核级方案

本工具仅用于**自有主机的安全自查与防护**。它只读取本机进程、服务、驱动、注册表与文件元数据，
不采集、不上传、不联网回传任何数据——所有数据都留在本机，HTTP 服务仅监听 `127.0.0.1`。

请勿将本工具用于未经授权的系统。
