# 银狐进程监视器 · SilverFox Process Sentinel

> 一个面向 Windows 的**桌面级进程行为监视工具**，用于发现银狐（SilverFox）木马及其变种的落地痕迹。
>
> **定位**：不是杀毒软件，也不是 EDR 替代品。它是一套**透明、可读、可改**的检测规则 +
> 一个零依赖的本地监视界面，适合在中招后做人工排查，或者作为理解银狐攻击链的学习样本。
> 能力边界请务必读第五节 —— 它**看不到纯内存执行、rootkit、短命进程**，
> 这些需要内核级方案。

BYOVD 驱动、hosts 劫持、Defender 排除项篡改等银狐全攻击链环节。

## 一、快速开始

> ⚠️ **如果你的机器开启了「智能应用控制」(Smart App Control)，请用 `.bat` 启动，
> 不要直接双击打包的 `.exe`。**
> 该策略会拦截未签名的自编译程序（`WinError 4551`，事件日志
> `Microsoft-Windows-CodeIntegrity/Operational` Id 3033/3077 可查）。
> 这是 Windows 自身的安全策略在正常工作，**不是程序有问题**，也**不建议为它关闭该策略**
> （关闭后需重置系统才能重新开启）。
> `启动银狐监视器.bat` 走的是已签名的 Python 解释器，不受影响。
>
> 本项目**不附带打包好的 exe**（体积大且必然未签名）。需要单文件分发的话，
> 可以自己用 PyInstaller 打包，参考 `docs` 里的说明或直接：
> `pyinstaller --onefile --noconsole --add-data "app;app" --name SilverFoxSentinel app/main.py`

### 方式 1：一键启动（推荐）

界面会以独立应用窗口打开（无地址栏、无标签页），首次扫描约需 5–20 秒。
**建议右键 → 以管理员身份运行**，否则部分检测能力受限（详见第五节）。

### 方式 2：调试启动（显示日志）

双击 **`调试启动（显示日志）.bat`**，会在控制台打印运行日志。
启动异常时用这个方式能看到具体报错。

### 方式 3：命令行

```bat
cd /d "本目录"
python app\main.py
```

### 停止

双击 **`停止监视器.bat`**，或直接关闭界面窗口。

### 依赖

仅一个第三方库：

```bat
pip install psutil
```

**启动器怎么找 Python**（每个候选都会先验证能否 `import psutil`，避免选到没装的解释器后静默失败）：

1. 项目根目录的 `python_path.txt`（内容为解释器完整路径）—— **用 venv / conda 时写这里**
2. 项目内 `runtime\pythonw.exe`（把便携版 Python 放进来即可）
3. Windows 官方 `py` 启动器（3.14 → 3.11 → 任意 3.x）
4. 系统 `PATH` 里的 `pythonw`

都找不到时会给出明确的安装指引。也可以直接命令行跑：`python app\main.py`。

> 为什么要逐个验证：一台机器上常有多个 Python，
> `py -3` 未必是装了 psutil 的那个；而程序用 `pythonw` 启动、没有控制台，
> 选错解释器就会**静默崩溃**，用户只看到点了没反应。

## 三、检测能力

### 3.1 规则分类

| 前缀 | 类别 | 条数 | 代表规则 |
|---|---|---|---|
| `P` | 进程行为 | 25 | 伪装系统进程、PPID 欺骗、签名伪造、C2 外联、命令行破坏 |
| `T` | 计划任务 | 7 | 冒用系统更新任务名、隐藏高频任务、AI 生成式长句任务名 |
| `S` | 系统服务 | 4 | 服务二进制位于非常规目录、伪装扩展名 |
| `D` | 内核驱动 | 4 | BYOVD 易受攻击驱动、驱动文件伪装扩展名 |
| `H` | hosts 劫持 | 2 | 安全厂商域名被指向回环地址 |
| `R` | 注册表 | 5 | Defender 大面积排除、银狐专用注册表键 |
| `F` | 文件系统 | 3 | 伪装扩展名的 PE 文件、银狐组合落地目录 |
| `X` | 深度扫描 | 3 | 白加黑侧加载、加载伪装扩展名模块 |

### 3.2 评分模型

```
风险分 = min(100, 最高权重 + 0.35 × 其余权重之和)

≥80 严重(critical) | ≥55 高危(high) | ≥30 可疑(medium) | ≥10 关注(low)
```

该模型的设计意图：**避免"5 条低危规则叠加"压过"1 条严重规则"**，
同时保留多条弱信号相互印证时的加成意义。

### 3.3 关键设计取舍

本工具的核心难点不是"能不能检出"，而是**误报控制**。开发过程中做过几轮实测收紧，
以下是几个有代表性的决策（都写在代码注释里）：

- **不凭缺失数据定罪。** 签名"尚未校验"或"校验失败"都不算未签名，
  只有明确判定为 `unsigned / forged / untrusted` 才触发签名相关规则。
  否则首轮扫描会满屏红点。
- **目录判定必须带上下文。** Windows Defender 自身就安装在
  `C:\ProgramData\Microsoft\Windows Defender\Platform\<版本>\` 下，
  按"ProgramData 下的程序可疑"一刀切会把 Defender 判成木马。
  现在 ProgramData / AppData 只在**文件名为随机名或一级子目录为随机名**时才判可疑。
- **随机命名识别要排除品牌名。** `i4Tools`（爱思助手）、`AIDA64` 含数字且大小写混杂，
  朴素启发式会把它们判成随机名。现在先做"是否像英文单词"的音节结构判断。
- **术语匹配必须按词。** 银狐恶意任务名 `Our Empowering Procedure Standardization And`
  里的 "Empowering" 含子串 "power"，按子串匹配会被合法术语表误挡。
- **大目录排除要精确相等。** `C:\Users\<用户名>\AppData\Local\JetBrains\PyCharm2026.1`
  这种正常的开发工具排除项，不能算成"整个 `C:\Users` 被排除"。

### 3.4 实测误报水平

在开发机上（Windows，296 个进程、269 个计划任务、313 个服务、442 个驱动）实测：

| 指标 | 结果 |
|---|---|
| 严重(critical) 误报 | **0** |
| 高危(high) 误报 | **0** |
| 中危(medium) 误报 | 1（正在运行的 `powershell.exe` 带 `-ExecutionPolicy Bypass` 参数） |

该中危项属规则 `P011` 的已知行为：`-ExecutionPolicy Bypass` 在正规安装程序中也常见，
因此本条只给中等权重（50 分），单独出现不会升级为高危。

### 3.5 性能

实测（311 个进程的机器上）：

| 指标 | 初版 | 现在 | 提升 |
|---|---|---|---|
| 稳态单轮采集 | 9081 ms | **62 ms** | **145×** |
| 冷启动首轮 | 9081 ms | 2463 ms | 3.7× |

初版一次性向 psutil 索取全部字段，其中三项是「隐形杀手」：

| 字段 | 311 个进程耗时 | 处置 |
|---|---|---|
| `cmdline` | 5132 ms | 按 (pid, 创建时间) 缓存，每个进程一生只取一次 |
| `num_threads` | 1341 ms | 移到详情视图按需获取 |
| `status` | 1224 ms | 删除（原本没有任何地方用到） |

而 `cmdline` 的 5.1 秒里，**100% 来自 5 个受保护进程**（`LsaIso.exe`、`NgcIso.exe`、
3 个 `WUDFCompanionHost.exe`）—— 每个都要整整 1025 ms 才抛 `AccessDenied`。
它们的 `exe` / `username` / `memory_info` 都是毫秒级，**只有 cmdline 会阻塞**。

处置方式：按映像名记住这类进程（预置 3 个实测确认的名字 + 运行时自动学习），
同时跳过没有真实映像路径的系统伪进程（`System` / `Registry` / `Memory Compression`）。
为避免留下检测盲区，跳过条件额外要求「该进程确实住在 `System32`」——
若木马把映像名伪装成 `LsaIso.exe` 放到用户目录，命令行照常会被读取和分析。

剩余的 2.4 秒冷启动是**操作系统首次枚举进程句柄的一次性开销**（第二次遍历即降到 52 ms），
不是代码问题，只影响启动后的第一次扫描。

### 3.6 接口安全

界面由本地 HTTP 服务提供（仅监听 `127.0.0.1`）。**开发过程中的一次安全审计发现：
初版对 POST 请求不做任何来源校验**，于是任意网页都能用

```js
fetch('http://127.0.0.1:8787/api/kill', {method:'POST', mode:'no-cors',
      body: JSON.stringify({pid: 1234})})
```

这种「简单请求」（`Content-Type: text/plain`，不触发浏览器预检）把请求送到服务端，
而服务端照单全收。实测可成功终止任意进程 —— 也就能调用 `/api/shutdown`
**把监视器本身关掉**。对一个反木马工具来说这是致命的。

现在采用四层校验（全部在服务端强制）：

1. **会话令牌**：每次启动生成随机令牌，注入页面 `<meta>`，POST 必须带 `X-Yinhu-Token` 头。
   自定义头会强制浏览器发预检请求，跨域预检必然失败 —— 请求根本发不出去。
2. **Origin 校验**：浏览器跨域请求必带 `Origin`，非同源一律拒绝。
3. **Host 校验**：必须是回环地址，防 DNS 重绑定。
4. **Content-Type 校验**：必须是 `application/json`，挡掉表单与 `text/plain` 提交。

另外：请求体上限 256 KB（防本地内存耗尽）；`PID 0 / 4` 等系统关键进程在接口层显式拒绝；
`/static/` 路径穿越已拦截。以上均有自动化回归用例覆盖。


### 3.7 已知项机制（让误报可被安全忽略）

安全工具最大的敌人不是漏报，而是**误报导致的告警脱敏** ——
用户被误报烦到之后，真正的告警也不看了。

直接删规则或按规则号全局忽略是**危险**的：那些规则恰恰也是攻击者的常用手法。
本项目改为「**带守卫哈希的已知项**」：

一条已知项 = 「规则号」+「匹配条件」+「**被执行的脚本文件的 SHA-256**」，三者都满足才忽略。

* 匹配条件限定到**具体对象**（如"命令行里必须含 `my-watchdog.ps1`"），不是"凡是这条规则都不报"；
* 守卫哈希绑定**被执行的脚本** —— 内容一旦变化（哪怕一个字节），哈希对不上，
  **忽略立即失效、告警自动回来**。攻击者替换脚本不会被静默放过；
* 守卫文件不存在时同样按"忽略失效"处理（宁可多报，不可漏报）。

用法：在告警详情里点「标记为已知项」，确认框会显示将要绑定的文件与哈希；
「规则与 IOC」页的「安全状态」面板里有已知项列表，可逐条移除。

已知项文件位于 `app/whitelist.json`，**有意放进 `app/` 让它被完整性自检覆盖** ——
绕过界面直接改白名单来掩盖告警，会触发"程序文件已被改动"的严重告警。

### 3.8 第二轮审计：三处自身误报

首轮把误报压到 0 之后，做了一次针对「工具会不会误判自己/系统」的专项审计，
又发现三处 —— 都是**工具在真实环境里会天天遇到**的，不是边角案例：

| 问题 | 现象 | 修正 |
|---|---|---|
| **X003 白加黑规则误判 MSIX 应用** | `pwsh.exe`（PowerShell 7，装在 `D:\WindowsApps\Microsoft.PowerShell_*`）加载同目录的 .NET DLL，被判定为白加黑 | MSIX / Store 应用的 DLL 由**包签名整体保护、不单独做 Authenticode 签名**，因此排除 `\WindowsApps\` 目录 |
| **单条规则重复计分导致分数爆表** | X003 每加载一个可疑 DLL 就产出一条 finding，`pwsh.exe` 一次 15 个 → 15 × 82 分，分数顶到 100 判成「严重」 | 深度扫描改为**按规则聚合**：一条 finding 带模块列表与计数，不再逐条累加 |
| **工具把自己的子进程判成木马** | 签名校验用 `powershell -EncodedCommand` 调用，正好命中 P010「内存加载/下载执行」→ 把自己的校验进程判成严重风险 | ① 排除本工具自己拉起的子进程（`ppid == 自身 PID`）；② 把 `-EncodedCommand` 从 P010 拆成独立的 **P010B**，权重降到中等（55）—— 该手法在 SCCM / Intune / 各类安装程序中同样常见，单独出现不足以定性 |

修正后的真机结果：**严重 0 / 高危 0 / 中危 1**，唯一那条是真实观察 ——
一个上一轮会话遗留的定时任务正在执行
`powershell.exe -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File ...my-watchdog.ps1`
（隐藏窗口 + 绕过策略 + 执行用户目录下的脚本文件，给中等权重是合理的）。

## 五、能力边界（请务必阅读）

这是一个**行为检测辅助工具**，不是杀毒软件，也不是 EDR。它的确定性局限：

**检测不到的场景**

- **纯内存执行**：银狐常用"读同目录 jpg/xml → 解密 shellcode → 内存执行"，磁盘上无 PE 落地。
  用户态轮询式监控看不到这类行为，需要 EDR 的内核回调 / ETW。
- **内核级隐藏**：若已加载 rootkit 驱动隐藏进程，本工具读到的进程列表本身就是不完整的。
- **BYOVD 之后的静默期**：银狐用易受攻击驱动强杀安全软件后，其行为可能不再产生可观测事件。
- **短命进程**：默认 3 秒采样一次，存活不足一个采样周期的进程会被漏掉。
- **DLL 注入到合法进程**：注入后的恶意代码在合法进程地址空间内运行，进程名与路径都正常。
  本工具只能通过"加载了非常规模块"间接发现，且需要管理员权限。

**权限限制**

| 能力 | 普通用户 | 管理员 |
|---|---|---|
| 进程列表 / 命令行 / 路径 | 大部分可读 | 完整 |
| 全局网络连接归属 | 部分缺失 | 完整 |
| Defender 排除项读取 | ❌ 读不到 | ✅ |
| 受保护进程的加载模块 | ❌ | ✅ |

**其他**

- 无法替代全盘杀毒扫描与专业 EDR。
- 规则基于公开报告，银狐是持续迭代的黑产工具，新变种可能绕过现有规则。
- 采样式监控天然存在时间窗口，不是实时阻断。
- **受保护进程（PPL / 安全隔离）的命令行无法读取**（`LsaIso.exe`、`NgcIso.exe`、
  `WUDFCompanionHost.exe`），工具会标注「受保护进程，系统拒绝读取」而非静默留空。
  这些进程的路径、签名、网络连接、加载模块等其它维度仍然正常参与检测。

### 5.x 「名字随机性」启发式的实测局限（重要）

银狐会用随机命名（`SXRh6d` / `cgL18U72` / `bcCfOw`）来逃避识别，
本项目用启发式判断"名字是否像随机串"。**这个启发式有明确的天花板，如实公布：**

在真实语料上（**1470 个**合法名字：进程名、服务名、驱动名、计划任务名、
`Program Files` 子目录名）实测：

| 指标 | 数值 |
|---|---|
| 把合法名字误判为随机 | **176 / 1470 ≈ 12%** |
| 漏判真实随机名 | 3 / 18 |

误判集中在 Windows 自带的服务/驱动缩写名上，例如
`AppIDSvc`、`BthA2dp`、`ApxSvc`、`CDPSvc`、`AmdPPM`、`AsyncMac`。

**为什么实际使用中没有暴露成误报**：这条启发式**只作加分项**，
调用处一律叠加"未签名 / 根证书不受信任"等条件才定罪，
而系统服务与驱动都有微软签名，因此不会触发。

**仍然存在的风险**：如果你机器上有**未签名**的软件，且它的名字恰好是这种缩写风格，
可能被报为可疑。用「已知项」忽略即可。

我们做过参数扫描（元音比例阈值、连续辅音阈值、大小写跳变次数等组合），
**没有任何一组参数能同时降低误报与漏报** —— 这是"按名字猜随机性"这一思路的固有限制，
不是实现问题。改用它需要真正的统计模型（字符 n-gram / 困惑度），那会显著增加依赖与开销，
本项目选择了"保持轻量 + 如实说明"。

## 六、发现威胁后的处置流程

> ⚠️ 银狐具备多阶段冗余设计：CNCERT 报告指出其执行链设置 6 个计划任务，
> **清除单个环节后其余载荷仍可运行**。只杀进程几乎必然被重新拉起。

1. **先取证，后清理。** 立即用「导出报告」保存当前状态（含哈希与完整路径）。
   条件允许时先对内存做镜像——磁盘上可能几乎没有痕迹。
2. **断网。** 拔网线 / 关 Wi-Fi，阻断 C2 与横向移动。
3. **不要急着关机。** 关机可能触发部分变种的破坏逻辑，也会丢失内存证据。
4. **按顺序清理**（每一步都做，不能跳）：
   - 计划任务（重点：`\Microsoft\Windows\AppID\` 下的、隐藏的、每分钟重复的）
   - 系统服务与内核驱动（`driverquery` 核对）
   - 注册表 `Run` 键与银狐专用键（`HKLM\SOFTWARE\JDBCC`）
   - Defender 排除项（`Exclusions\Paths` / `Exclusions\Processes`）
   - hosts 文件中的回环劫持条目
   - 常驻目录（`C:\Users\Public\`、`C:\ProgramData\`、`C:\Windows\Temp\`、`%APPDATA%`）
5. **改密码。** 尤其是财务系统、即时通讯（银狐主要目标是财务人员与 IM 账号）。
6. **全盘杀毒；企业环境建议直接重装。** 银狐的免杀与持久化能力使得"清干净"很难验证。
7. **上报。** 企业用户应同步安全团队；可向 CNCERT 报送样本与 IOC。

## 九、安全性说明（威胁模型 · 加固措施 · 能力边界）

### 9.1 它会不会被篡改？——**会，而且必须承认这一点**

**实测证据**：程序目录的 ACL 显示，`NT AUTHORITY\SYSTEM`、`BUILTIN\Administrators`
和当前用户账户对本目录都是 `FullControl`。而本工具以当前用户身份运行。
结论：**任何以相同权限运行的恶意程序，都可以直接修改规则文件、或者干脆结束本进程。**

这不是本工具特有的缺陷，而是所有**用户态**安全工具的固有上限。专业 EDR 靠两样东西解决它：
内核驱动 + 以 **PPL（受保护进程）** 身份运行 —— 后者需要 EV 代码签名证书并通过微软审核，
纯 Python 脚本做不到。

**已实现的缓解：程序文件完整性自检**

- 首次运行为 `app/` 下全部代码与前端文件建立 SHA-256 基线，此后每次启动、
  以及运行期间每 5 分钟重新比对；
- 一旦发现文件被改动，**顶栏状态灯变红**、告警时间线出现严重级告警、
  「安全状态」面板列出被改动的具体文件；
- 也可以在命令行独立校验：`python app\main.py --verify-only`
  （正常退出码 0，检测到改动退出码 2，便于脚本化）；
- 确认改动是自己做的（例如更新了 IOC）后，可在界面上重建基线。

**这个机制能做什么、不能做什么（说清楚）**

| 能做 | 不能做 |
|---|---|
| 发现意外损坏（磁盘错误、拷贝不完整、更新中断） | 发现"攻击者同时改了代码和基线"的情况 |
| 发现**顺手改一把**的普通恶意程序（绝大多数木马不会专门针对本工具做免杀，更可能粗暴替换规则文件） | 阻止攻击者直接结束本进程 |
| 让用户随时确认手上的副本没被人动过 | 阻止攻击者给本程序打补丁 |

**要真正抗篡改，正确做法是**：把程序装到受保护目录（如 `C:\Program Files\`），
由管理员控制文件写权限，并以专用低权限账户运行界面。这属于部署层面的加固，
本工具不自动做（因为会显著提高使用门槛）。

### 9.2 它会不会给其他攻击留下漏洞？——已实测，并修掉了一个真问题

**实测的攻击面**（脚本 `_dev/audit_surface.py` 可复跑）：

| 项目 | 实测结果 |
|---|---|
| 监听范围 | `127.0.0.1:8787`，**只绑回环地址**；从局域网 IP `192.168.1.50:8787` 连接被拒（ConnectionRefused）；未绑定 `0.0.0.0` |
| 网络外联 | 运行 40 秒，该进程及其全部子进程的**非回环连接数 = 0** |
| 子进程 | 仅签名校验期间短暂出现的 PowerShell（校验完即退出） |
| 运行权限 | 当前用户（**不是** SYSTEM） |

**修掉的一个真实注入隐患**：签名校验需要把一批文件路径交给 PowerShell。
初版是把路径**拼进脚本文本**（`$paths=@('...','...')`）——
虽然转义了单引号，但 Windows 文件名在 NTFS 原生接口下可以包含**换行等控制字符**，
而待校验路径来自**进程枚举**（攻击者可控输入），理论上可注入额外语句；
而这些 PowerShell 是以当前用户（通常是管理员）身份运行的。

修正：① 剔除含控制字符的路径；② 路径改为**经临时文件传递**，彻底不做字符串拼接。

**已实现的写操作防护**（详见 3.6 节）：会话令牌 + Origin 同源 + Host 回环 + Content-Type
四层校验，另有请求体上限、受保护 PID 拒绝、静态文件路径穿越校验。
9 条攻击路径的自动化回归用例全部通过。

**仍然存在的风险（诚实列出）**：

- 以管理员身份运行时，本进程被攻破即等于管理员权限失守 —— 因此**不建议长期以管理员身份挂着**，
  只在需要完整检测能力时临时提权；
- 报告导出为 HTML 文件，用浏览器打开时理论上存在本地 HTML 的常规风险
  （内容已做转义，且数据来源是本机进程信息）；
- 界面依赖 Edge 渲染，浏览器的漏洞面属于 Edge 而非本工具。

### 9.3 检测内容真不真？——分级标注来源

**规则里没有一条是我编的。** 但来源的可靠度分两档，应当说清楚：

| 来源档位 | 具体来源 | 说明 |
|---|---|---|
| **一手（逐字摘录）** | CNCERT & 天融信《关于"银狐"木马"甲蚁（G01）团伙攻击态势深入分析报告》2026-09 | 我下载了官方 PDF 并用 pypdf 提取全文，IOC 是**逐字摘的**。计划任务名、落地路径、C2 地址、伪造签名主体、Defender 排除项等均出自此报告 |
| **二手（网页摘要）** | FreeBuf 七阶段攻击链分析、火绒安全实验室 BYOVD 分析（看雪论坛转载）、先知社区应急复盘、博客园 DoH 变种逆向 | 通过网页抓取 + 摘要获得。**具体字符串可能与原文有出入**，建议以原文为准 |

**我做不到的事（必须说明）**：我**没有拿到任何银狐样本**，
因此无法独立验证每条 IOC 的准确性，也无法确认这些 IOC 当前是否仍在被使用。
IOC 会随木马迭代失效 —— 银狐是"黑产 SaaS"式持续运营的家族，
CNCERT 报告明确指出其**服务端按次打包载荷、同名文件哈希各不相同**，
所以基于固定文件名的黑名单本来就容易被绕过。

**这也是为什么规则引擎的重心是行为特征而不是 IOC**：
即使所有 IOC 全部过期，"伪装系统进程 + 签名伪造 + 计划任务持久化 + BYOVD 驱动 + hosts 劫持"
这些行为规则依然有效。IOC 只是加分项。

### 9.4 和专业检测工具差在哪里？

| 能力 | 本工具 | 专业 EDR / 杀毒软件 |
|---|---|---|
| 进程创建事件 | **3 秒轮询**，存活不足一个周期的进程会漏 | 内核回调 `PsSetCreateProcessNotifyRoutineEx`，零漏报 |
| 无文件/纯内存执行 | **看不到**（银狐主力手法） | ETW Threat Intelligence + 内存扫描 + AMSI |
| DLL 注入 | 只能靠"加载了非常规模块"间接推测 | 内核回调 + 内存区域权限检查（RWX 检测） |
| 网络层 | 只读本机连接表（无域名、无内容） | 网络流量解析、DNS/HTTP 层检测、NDR |
| 抗篡改 | 用户态自校验，可被同权限攻击者绕过 | 内核驱动 + PPL 保护 |
| 实时阻断 | **不能**，只能事后告警 | 可在行为发生前拦截 |
| 文件特征库 | 无 | 百万级特征 + 云查杀 + 机器学习 |
| 处置能力 | 结束进程、打开文件位置 | 隔离、回滚、全网联动 |
| 免杀对抗 | 无 | 持续更新 + 沙箱 + 动态行为分析 |

**它比专业工具强的地方只有两点**，但这两点对个人用户确实有价值：

1. **完全透明**：56 条规则、全部 IOC、每一条的判断依据都写在明文文件里，你可以逐条读、
   逐条改。商业 EDR 的规则引擎是黑盒。
2. **零依赖、零联网、零成本**：不需要控制台、不需要订阅、不上传任何数据。
   适合做"第一时间的自查"，或者作为专业工具的补充视角。

**一句话定位**：它大致相当于"Sysinternals + 一套定制排查脚本"的自动化版本，
**不是 EDR 的替代品**。中招之后想彻底确认是否清除干净，仍然需要专业工具或重装系统。

### 9.5 能不能完全本地化、不联网、不开网页？

**联网方面：本来就不联网。** 实测 40 秒内该进程及全部子进程的**非回环连接数为 0**；
程序内没有任何向外部服务器发送数据的代码路径。所有采集数据只存在于本机内存、
以及你主动导出的报告文件里。

**"不开网页"方面：目前做不到完全脱离浏览器。** 这是一个明确的设计取舍：

- 界面是**本地**页面（`http://127.0.0.1:<端口>`），不经过任何网络；
- 但它需要 Edge/Chrome 作为渲染引擎（以 `--app` 模式开一个无地址栏的独立窗口）；
- 选这个方案的原因：**零额外运行时依赖**。用 Electron 要拖进来上百 MB，
  用 tkinter 则界面表现力明显不足（且部分 Python 发行版不自带 tkinter）。

如果你确实要求"完全不使用浏览器"，有两条路，都需要额外安装东西：

1. 改用 tkinter 重写界面 —— 彻底脱离浏览器，但界面会明显变朴素；
2. 用 `pywebview` 换成 WebView2 内核 —— 本质上仍是网页渲染，只是不显示浏览器外壳。

**当前方案的实际风险**：本地页面不暴露到网络，浏览器只用来渲染本地内容，
不加载任何远程资源（页面带 CSP 头，`script-src 'self'`）。

### 9.6 端口能不能检查、能不能改？

**能查。** 三种方式：

1. **界面**：「规则与 IOC」页顶部的「安全状态」面板直接显示 `监听地址 127.0.0.1:8787`；
2. **文件**：程序运行时会把自己实际使用的端口写入 `runtime_port.txt`；
3. **命令行**：`netstat -ano | findstr LISTENING | findstr 127.0.0.1`，
   再用 `tasklist /FI "PID eq <PID>"` 对上是哪个进程。

**能改。** 支持命令行参数：

```bat
python app\main.py --port 9000          :: 指定端口
python app\main.py --no-window          :: 只起服务，不自动开窗口
python app\main.py --host 0.0.0.0       :: ⚠ 会开放给局域网，不建议
python app\main.py --verify-only        :: 只做完整性校验后退出
```

端口范围默认在 `8787-8816` 之间自动挑选空闲端口。
指定 `--host` 为非回环地址时会打印醒目警告 —— 那会让同网段的其他机器访问到你的进程列表，
**强烈不建议**。

**顺带回答"工具能不能检查端口"**：能。规则 `P025` 会标记"无签名程序 + 用户目录 + 监听端口"
的组合；界面进程详情里每个进程都列出它的网络连接与监听状态。

### 9.7 威胁模型：同用户攻击者能做什么、我们怎么应对

这是用户态安全工具绕不开的问题，如实说清。

**前提**：攻击者已经能以你的身份运行代码（这是反木马工具的常规假设）。

| 攻击手法 | 是否可行 | 应对 |
|---|---|---|
| 直接结束监视器进程 | ✅ 可行 | 无法防御（无内核驱动/PPL）。这是所有用户态工具的固有上限 |
| 改 `app/rules.py` 删掉检测规则 | ✅ 可行（若程序目录可写） | 完整性自检会报「程序文件已被改动」 |
| 改 `python_path.txt` 让启动器执行他的程序 | ✅ 可行（若程序目录可写） | **程序目录已收紧为仅管理员可写**（见下） |
| 删掉基线文件让自检哑火 | ✅ 可行 | 哨兵文件在独立位置，会报「基线丢失」 |
| 加一条已知项掩盖自己的告警 | ✅ 可行 | 已知项**绑定被执行文件的 SHA-256**，文件一变忽略即失效 |
| 用「加入已知项」这个日常操作洗白篡改 | ✅ 曾可行 | 已修：基线刷新**只接受 `whitelist.json` 的差异**（见下） |

**关键加固一：程序目录收紧为仅管理员可写**

`D:\<程序目录>` 默认继承 `Authenticated Users: Modify` ——
任何登录用户都能改 `python_path.txt`，让启动器去执行他的程序，
而**监视器根本不会启动，自检告警永远不会出现**。
所以光靠"把配置文件纳入基线"救不了场，必须做结构性修复：

```powershell
# 以管理员身份执行（把 <路径> 换成实际程序目录）
icacls "<路径>" /inheritance:d /T /C
icacls "<路径>" /remove:g "NT AUTHORITY\Authenticated Users" "BUILTIN\Users" /T /C
icacls "<路径>" /grant:r "NT AUTHORITY\Authenticated Users:(OI)(CI)(RX)" /T /C
icacls "<路径>" /grant:r "BUILTIN\Administrators:(OI)(CI)(F)" /T /C
icacls "<路径>" /setowner "BUILTIN\Administrators" /T /C
```

⚠️ **在 Program Files 下新建文件夹时，创建者账户会被自动授予 FullControl** ——
"放在 Program Files 就安全"这个假设不成立，必须显式清理 ACL。

**关键加固二：完整性基线刷新不再"全量赦免"**

曾经的实现是：界面上增删一条已知项 → 重算 `app/` 下**全部文件**的哈希并整体覆盖基线。
这是个严重漏洞 —— 攻击者改掉 `rules.py` 后，用户只要对**任何一条无关告警**
点一次「加入已知项」，篡改就被写进新基线、告警消失，而触发动作完全日常。

现在的语义：**除 `whitelist.json` 之外的任何差异都拒绝刷新**，
保留完整性告警并把差异清单返回给界面展示。
全量重建只保留给界面上那个显式按钮（用户明确知道自己在做什么）。

**关键加固三：`python_path.txt` 纳入完整性基线**

启动器会执行它里面写的解释器路径，所以它必须被自检覆盖 ——
改动会触发「程序文件已被改动」。启动器还会**回显实际使用的解释器路径**，
被换成陌生路径时一眼可见。

**仍然做不到的**（不要抱幻想）：

- 攻击者可以直接 `taskkill` 结束监视器 —— 用户态工具无法阻止
- 攻击者若能提权到管理员，上述 ACL 保护即失效
- 纯内存执行、rootkit、DLL 注入到合法进程 —— 需要内核级方案

本工具仅用于**自有主机的安全自查与防护**。它只读取本机进程、服务、驱动、注册表与文件元数据，
